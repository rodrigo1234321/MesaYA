## 1. Problema Diagnosticado (H01 / D01)
- En el commit baseline `7bcddf6`, los esquemas `schema.prisma` y `schema.supabase.prisma` declaraban:
  ```prisma
  model StaffUser {
    ...
    pinFingerprint   String?     // huella determinística HMAC (P0-04 concurrencia)
    ...
    @@unique([restaurantId, pinFingerprint])
  }
  ```
- Sin embargo, en el historial de migraciones de PostgreSQL (`packages/api/prisma/migrations-postgres/`), **ninguna migración agregaba la columna `pinFingerprint` ni creaba el índice único `"StaffUser_restaurantId_pinFingerprint_key"`**.
- La última migración existente era `20260911110000_account_settlement_responsible_staff`.
- Cualquier despliegue limpio o sincronizado con `prisma migrate deploy` en PostgreSQL fallaba o dejaba al sistema sin la columna y sin la protección de unicidad bajo concurrencia.

---

## 2. Solución Implementada
1. Se creó la migración aditiva y segura en:  
   `packages/api/prisma/migrations-postgres/20260914000000_add_staff_pin_fingerprint/migration.sql`
   ```sql
   -- AlterTable
   ALTER TABLE "StaffUser" ADD COLUMN IF NOT EXISTS "pinFingerprint" TEXT;

   -- CreateIndex
   CREATE UNIQUE INDEX IF NOT EXISTS "StaffUser_restaurantId_pinFingerprint_key" ON "StaffUser"("restaurantId", "pinFingerprint");
   ```
2. Tipado estricto: Se utilizó `TEXT` (tipo nativo de Postgres para `String?` en Prisma) en lugar de `VARCHAR(64)` para garantizar compatibilidad con el mapeo por defecto del schema de Prisma.
3. Compatibilidad hacia atrás: La columna es nullable (`TEXT`), permitiendo la coexistencia con registros históricos previos.
4. Sincronización de esquemas: Se normalizaron los finales de línea CRLF en `schema.supabase.prisma` y se validó con `scripts/sync_supabase_schema.js --check`.
